# 贡献与发布工作流

## 贡献与合并

可信协作者可以直接将已准备好的变更合并到 `main`，并同步到生产发布仓库；PR 和额外 GitHub 人工批准不是合并前提。自动 CI/CD 仍会运行适用的 Node、Python、桌面浏览器检查，生成源代码发行包，并在部署期间执行备份、数据保留与健康检查。检查失败时自动停止发布；若代码切换后的启动或数据保留校验失败，网关回滚代码并保留当前数据库。

实现者可按变更风险选择本地测试、发行包预检或独立 reviewer 检查。新行为、错误处理和数据迁移适合先在隔离临时数据库、测试账号、注册码、端口和目录中验证；迁移检查应覆盖旧记录及其 ID、评分、完成状态和账号数据。桌面浏览器是默认用户界面；移动端适配只在用户提出时纳入范围。独立 reviewer 是可选质量帮助，不是合并或上传的门槛。不得使用生产数据进行开发测试。

## 生产发布

生产发布由 `Sigmit64/puzzle-database` 的 `main` 自动触发。发布前由自动化创建 SQLite 在线备份和权限受限的代码回滚副本；业务状态位于 `/var/lib/puzarchive`，发布源代码不得复制或覆盖该目录中的文件。自动化将发行包放入独立 staging 目录，核对包与提交后短暂停止服务、原子切换代码并启动一次。不要借此修改环境文件、成员配置、注册码门控、Nginx 或证书设置。

发布后只做只读健康检查和备份校验，并在服务器内存中比较旧字段和备份数据；只报告聚合计数和相等性布尔值。不要导出成员 ID、凭据、会话值、注册码、哈希或配置指纹，也不要用注册、审核、投票或评分请求测试生产。如果启动、只读健康检查或数据保留校验失败，停止发布并回滚代码源目录，保留数据库和成员配置原样；修复后可重新合并并触发自动发布。

生产工作流会串行执行发布，并拒绝活动中的重复提交。GitHub Actions 的部署凭据仅限生产部署任务；PR 和上游仓库任务不取得部署凭据。有关自动化和运维网关的细节见 [CI/CD](ci-cd.md)。
